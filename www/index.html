Why a monorepo and why Nx

The case for one repository, the case against it, and the specific problem Nx solves that npm workspaces does not.

Most front-end estates around an AEM installation start as one repository per deliverable. There is a repo for the marketing site bundle, a repo for the account portal, a repo for the design system, and a repo of shared utilities that nobody wants to own. Each publishes to a private registry. Each has its own pipeline. This works for about eighteen months.

What breaks it is not the repository count. It is the release ordering. A change to the design system needs a version bump, a publish, a dependency bump in three consumers, three pull requests, three reviews, and three deploys, all in order, before anyone can see it on a page. Teams learn to batch. Batches get large. Large batches get reverted as a unit. The design system stops changing.

Not a size argument. Monorepos are often sold on scale. The real payoff at AEM-sized estates is atomicity: one commit changes the library and every consumer, and CI proves it before merge.

A monorepo removes the ordering problem by removing the version boundary. The shared library and its three consumers are in the same commit. If the change breaks the portal, CI says so on the pull request rather than four days later during the portal's own release.

What you actually give up

Be honest about the costs, because they are real and they land on different people than the benefits do.

  • Checkout size and clone time. A workspace with four apps and forty libraries is a bigger clone than any one of them. Shallow clones and partial clones help. Someone has to configure them.
  • Blast radius of a bad merge. One broken commit on the trunk blocks everyone, not one team. You need the pipeline to be fast and trustworthy, or people will start merging around it.
  • Ownership goes fuzzy. With no repository boundary, there is no natural access boundary. You need CODEOWNERS and lint rules to replace what repository permissions used to do for free.
  • Tooling coupling. Everyone is on the same TypeScript version, the same lint config, the same test runner. Upgrades become a coordinated project instead of an individual one. This is usually a benefit, but it is a benefit that arrives as a large piece of work every eighteen months.

If you have two applications and one shared library, a monorepo is overhead you do not need. The break-even is somewhere around three consumers of a shared library, or two teams that need to ship on independent schedules against shared code.

Why not just npm workspaces

Package managers give you the layout. npm, pnpm and Yarn all hoist dependencies and link local packages, which is genuinely most of what a monorepo needs day to day.

What they do not give you is any idea of what depends on what at the source level, and therefore no way to answer the only question that matters in CI: given this diff, what has to be rebuilt and retested? Without an answer, every pull request runs everything. A workspace with four apps and forty libraries runs a twenty-five minute pipeline to validate a copy change in a footer.

The one-sentence version

A package manager knows your packages. A build system knows your graph. Nx is the graph, plus a cache keyed on it.

What Nx adds, concretely

Three things, in order of how much time they save.

  1. A project graph derived from your imports. Nx parses TypeScript imports and package dependencies and builds a directed graph of projects. You do not maintain it. It is derived, so it cannot drift from the code.
  2. Affected commands. Given two git revisions, Nx computes the changed files, maps them to projects, then walks the graph upward to every project that transitively depends on them. Chapter 2 has a widget that lets you feel this.
  3. A computation cache. Every task is hashed from its inputs: source files, dependency outputs, the command, the relevant config. Same hash, same output, replayed from cache instead of recomputed. Shared across machines if you point it at a remote cache.

The cache is what makes the graph pay. Affected alone still rebuilds a library the first time each machine sees it. Affected plus a shared cache means CI usually restores rather than runs, and the pipeline time tracks the size of the change rather than the size of the repository.

Where Nx does not help

It does not solve the AEM half of the problem. Nx will produce you a clean, cache-friendly bundle. Getting that bundle into a client library, or behind the dispatcher, or in front of the Universal Editor, is Part II, and none of it is Nx's concern. Be careful about teams that adopt Nx and then declare the AEM integration a "packaging detail". It is most of the work.

It also does not make a bad library boundary good. Nx will happily let you build a single shared library that every project imports, and then correctly tell you that every change rebuilds everything. That is not Nx being slow. That is the graph telling you the truth about your design. Chapter 4 is about fixing that.

Self-check 1.1

  3. No. Affected walks upward to dependents of what changed, not downward through every app's full dependency tree. Unchanged dependencies are restored from cache, not rebuilt.

Self-check 1.2

The Nx mental model

Projects, targets, the graph, inputs and the hash. Four ideas. Everything else in Nx is a consequence of them.

Nx is easier to reason about once you stop thinking of it as a CLI and start thinking of it as a function. It takes your workspace and a git range, and returns a list of tasks with a hash attached to each. Everything else is plumbing around that function.

Projects

A project is a directory with a project configuration. That configuration can be an explicit project.json, a package.json with an nx key, or nothing at all when a plugin infers it. Modern Nx leans hard on inference: if you have a vite.config.ts, the Vite plugin infers build, test and serve targets for you without any config file.

Inference is a real change. If you are reading a tutorial that hand-writes every target in project.json, it predates plugin inference. nx show project <name> prints the effective, merged configuration including inferred targets. Trust that over the file.

Targets

A target is a named thing a project can do: build, test, lint, build-aem. Targets declare their outputs so Nx knows what to cache, and declare dependsOn so Nx knows what has to happen first. The token ^build means "the build target of every project I depend on".

Most of this belongs in targetDefaults in nx.json rather than repeated per project.

Inputs, and why they are the whole game

Nx caches a task by hashing its inputs. Get the inputs wrong in one direction and you get stale output served from cache. Get them wrong in the other direction and the cache never hits. Both failures look like "Nx is unreliable" to the team.

namedInputs is where you say what a file set means. The important one is production: the set of files that can change a build output. Test files, stories and specs cannot, so they are excluded. That exclusion is why editing a spec file does not invalidate a downstream app's build.

The failure mode nobody catches in review

If a build reads a file that is not in its inputs, the cache will serve stale output the moment only that file changes. AEM projects hit this with brand token files, .env-style config, and anything generated by a Maven step. If a build reads it, it belongs in inputs, even if it lives outside the project directory.

The graph, and the direction that matters

Nx builds the dependency graph from your actual imports. When you run a build, it walks down that graph: build my dependencies first, then me. When you run affected, it walks up: find everything that transitively depends on what changed.

People get this backwards constantly, and the consequence is always the same surprise: "why does a one-line change in a formatting utility rebuild the entire workspace?" Because eight projects transitively import it. Here is that graph, live.

Affected simulator

Tap a project to mark it as touched. Arrows point from a project to the things it imports, so the highlight travels against the arrows.

Touch shared-util-format and all eight projects are affected, because everything reaches it eventually. Touch site and exactly one project is affected, because nothing imports an application. That asymmetry is the entire design pressure on your library layout, and chapter 4 is about how to use it deliberately.

Verify this yourself. The closure in the widget above is computed by the same breadth-first walk Nx uses, and the repository ships tools/verify-affected-closure.mjs, which recomputes it a second way and asserts the two agree. Graph maths in a teaching aid is worth checking.

The hash

Once Nx knows the task list, each task gets a hash built from its resolved inputs, its dependencies' output hashes, the command line, and the relevant slice of configuration. That hash is the cache key. Two identical hashes anywhere, on any machine, mean the same output.

Exercise 2.1

  1. In any Nx workspace, run npx nx build <lib> twice. The second run should report a cache hit.
  2. Edit a *.spec.ts file in that library and build again. It should still hit, because specs are excluded from the production named input.
  3. Edit a source file and build again. It should miss.
  4. Now add a file the build reads but no input mentions, such as a JSON token file imported at build time, change only that file, and confirm you get a stale cache hit. That is the failure mode from the callout above, reproduced deliberately.

Standing up the workspace

The flags that matter on day one, the ones you will regret, and the four files that define the workspace forever.

Workspace generation is a five second command that fixes decisions you will live with for years. The prefix goes into every component selector. The directory layout goes into every import path. Neither is pleasant to change once forty libraries exist.

Generating it

As of Nx 23.2.1 the Angular presets are angular-monorepo and angular-standalone. Take the monorepo preset even if you only have one application today, because the standalone preset puts the application at the workspace root and converting later is tedious.

On --zoneless. This is a real flag in create-nx-workspace@23.2.1 and it requires Angular 21 or later. If you are pinned below that, drop it: the generator will refuse rather than fall back.

The four files

Everything structural lives in four files. Read them once, properly, and most Nx confusion goes away.

1. nx.json

Note build-aem in targetDefaults. That target does not exist yet, but declaring its caching and output behaviour once here means every project that later adds one inherits correct caching. Chapter 11 fills it in.

2. tsconfig.base.json

This is the import map for the whole workspace. Every library gets one path entry pointing at its barrel file, and every consumer imports the alias rather than a relative path.

Never point a path at a directory

An entry like "@acme/shared/*": ["libs/shared/*/src/index.ts"] looks convenient and destroys your boundaries. It lets any file reach into any library's internals, and the module-boundaries rule in chapter 5 cannot see through it. One alias per library, pointing at exactly one index.ts.

3. package.json

Keep the root package.json boring. One version of Angular, one version of TypeScript, one of everything. Per-project dependency versions are how you get two copies of RxJS in one bundle.

4. .nvmrc

One line. It is in sharedGlobals in nx.json, so bumping Node correctly invalidates every cached artifact in the workspace, which is what you want. A Node major upgrade can change esbuild output.

Directory layout

One directory level per scope. libs/<scope>/<type-name> scales to forty libraries without a naming committee, and the directory name is exactly the tag you will enforce in chapter 5.

Slicing into libraries

Two axes, five types, and a rule for where to draw the line. Chapter 2 showed why this decides your CI time.

The simulator in chapter 2 makes the design pressure obvious. Depth in the graph is expensive because it multiplies dependents. Breadth is cheap. So the goal of library slicing is to keep the widely-imported things small and stable, and push volatile code out to the leaves where nothing depends on it.

Two axes

Every library gets two tags. The first says who is allowed to import it. The second says what kind of thing it is.

TagMeaningExample
scope:sharedAnyone may import it.shared-ui
scope:checkoutOnly the checkout domain, plus apps.checkout-feature-cart
scope:accountOnly the account domain, plus apps.account-feature-profile
type:featureSmart. Routes, state, orchestration.checkout-feature-cart
type:uiDumb. Inputs in, outputs out, no HTTP.shared-ui
type:data-accessHTTP, GraphQL, AEM models, caching.shared-data-access-aem
type:utilPure functions. Often no Angular at all.shared-util-format
type:appAn application. Nothing imports it.site
Why type:util should not import Angular. It is the deepest node in the graph, so it is the most expensive to change. Keeping it framework-free means its tests are milliseconds and its build is a tsc pass, not an Angular compilation.

Generating them

Note --bundler=none on the util library. A library that only other libraries import does not need its own build output. Nx compiles it as part of the consumer. Giving every library a build target is a common way to double your CI time for no benefit.

The barrel is the API

The index.ts of a library is a public API, and should be treated with the same seriousness as one. Everything not exported there is private, and the boundary rule in chapter 5 enforces that.

A rule that survives contact with reality

Put code in a shared library when a second consumer needs it, not when you predict one will. Premature sharing is what produces the shared-util-format that everything imports and nobody dares change. Duplicating a 20 line helper across two features is cheaper than a bad graph edge.

How to split a library that grew too big

You will get this wrong at least once. The recovery is mechanical.

  1. Run npx nx graph --focus=shared-ui and look at who imports it.
  2. Identify the subset actually used by more than one consumer. That stays.
  3. Everything used by exactly one consumer moves into that consumer, or into a scope:-specific library.
  4. Move files, update the barrel, update tsconfig.base.json if a new library appeared, and let the compiler find the broken imports.
  5. Confirm with npx nx graph that the new library has fewer inbound edges than the old one.

Enforcing the boundaries

Tags are documentation until a lint rule fails the build. Here is the rule, its real option set, and the escape hatches you will need.

A convention that is not enforced is a convention that decays at exactly the rate your team hires. @nx/enforce-module-boundaries turns the tags from chapter 4 into a lint error, which turns them into a fact.

The rule

It lives in @nx/eslint-plugin and reads the tags from each project's configuration. Its full option set as of Nx 23.2.1:

OptionWhat it does
depConstraintsThe list of rules. Each entry has sourceTag or allSourceTags, plus onlyDependOnLibsWithTags, notDependOnLibsWithTags, bannedExternalImports or allowedExternalImports.
allowImport path globs that bypass all constraints. Use sparingly and comment every entry.
enforceBuildableLibDependencyStops a buildable library depending on a non-buildable one, which would produce an unpublishable artifact.
banTransitiveDependenciesRequires that anything you import is a direct dependency, not something you get for free through another package.
checkDynamicDependenciesExceptionsPaths exempt from the check on dynamic import() edges.
checkNestedExternalImportsAlso checks deep imports into external packages, not just the package root.
allowCircularSelfDependencyPermits a project importing its own alias, which otherwise reads as a cycle.
ignoredCircularDependenciesExplicit pairs to exclude from cycle detection while you unpick them.

The config

allSourceTags is an AND. The last constraint applies only to projects carrying both type:app and platform:node. A plain sourceTag matches a single tag. This is the cleanest way to express platform rules without a third axis of scope names.

What a violation looks like

Both of these are useful failures. The first means a presentational component started doing HTTP. The second means somebody reached for a pipe in the wrong place. Neither should be silenced.

The escape hatches, and when to use them

Three exist, in increasing order of how much explanation they need.

  1. Add a tag. Usually the honest fix. If a library genuinely needs to be importable by two scopes, it is scope:shared, and the question is whether it belongs there.
  2. allow globs. For structural exceptions: test setup, generated files, a codegen output directory. Every entry gets a comment saying why.
  3. An inline disable. // eslint-disable-next-line @nx/enforce-module-boundaries. Acceptable exactly once, with a linked ticket, during a migration. If your codebase has more than a handful, the constraints are wrong and you should change them rather than accumulate suppressions.

Circular dependencies

The rule also catches cycles. A cycle between two libraries is not a style problem, it is a statement that they are one library with a line drawn through it. The fix is almost always to extract the shared part downward into a type:util, not to add the pair to ignoredCircularDependencies. Use that option only to stop the bleeding while you do the extraction.

Angular inside the workspace

Signals, input(), zoneless change detection, and why all three matter more than usual when the host page is AEM.

Angular 22 is a different framework to the one most AEM integrations were written against. Standalone components are the only kind. Signals are the default reactive primitive. Zoneless is stable and, for embedded work, is the option you want. This chapter is the subset that changes how you write AEM-facing code.

Checked, not recalled

As of 10 September 2026, @angular/core is 22.1.6 and the zoneless provider is provideZonelessChangeDetection(), marked stable since 20.2. The older provideExperimentalZonelessChangeDetection name is gone. If you find a tutorial using it, the tutorial predates Angular 20.2.

Signals and input()

Signal inputs replace the @Input() decorator. They are read as functions, they are typed, and they participate in computed() without a lifecycle hook.

input.required has teeth. Reading a required input before it is set throws. In a custom element (chapter 11) that means reading it in the constructor throws, because attributes are applied after construction. Read inputs in a computed or in the template, never in a constructor.

Two-way with model(), events with output()

Zoneless, and why it matters here specifically

Zone.js works by monkey-patching every async primitive in the browser: setTimeout, Promise, addEventListener, XMLHttpRequest, and more. In a standalone Angular application that is invisible. On an AEM page it is not, because you are a guest.

  • AEM pages carry other scripts: analytics, personalisation, the author-mode editing overlay, a tag manager, and often a second framework from a different team. Zone.js patches globals for all of them.
  • Two Angular islands on one page, each with its own Zone.js, is a genuine conflict.
  • Zone.js is roughly 30 kB before compression, on a page that already ships AEM's own client libraries.

Removing Zone.js entirely also means removing the polyfill from the build. Nx and the Angular builder handle this when you generate with --zoneless, but check: a leftover zone.js entry in polyfills ships 30 kB of dead patching.

What breaks when you go zoneless

Anything that mutated a plain field and relied on Zone.js noticing. Third-party widgets that call back outside Angular, setTimeout callbacks that set a property, and any code doing this.items.push(x) on an array rendered in a template. The fix is to hold that state in a signal. There is no shortcut, and this is the real cost of the migration.

Where rxjs still belongs

Signals are for state. RxJS is still the right tool for event streams over time: debounced typeahead, websockets, retry with backoff. Convert at the boundary rather than picking a side.

  3. No. AEM has no opinion about your bundle contents. This is an engineering choice, not a platform rule.

  4. No. Signals work fine either way. Zoneless is a separate, compatible decision.

Tests, lint and the CI pipeline

A pipeline whose duration tracks the size of the diff, not the size of the repository. Plus the one action that makes affected correct on a merge queue.

The whole argument for Nx collapses if CI runs everything anyway. Getting affected correct in CI is a two-part problem: computing the right base SHA, and having a cache that survives between runs. Both have a standard answer.

The base SHA problem

Locally, --base=main is fine. In CI it is not, because the runner does a shallow clone with no main ref, and because on a merge queue the interesting comparison is against the last successful build, not the branch point.

nrwl/nx-set-shas solves this. It queries the workflow history and exports NX_BASE and NX_HEAD. Nx reads those environment variables automatically, so downstream steps need no flags.

Version check

AEM for front-end engineers

The smallest accurate model of AEM you can hold in your head and still make correct decisions with. Four boxes and one repository.

You do not need to know AEM. You need to know four things about it: that it is a content repository with a rendering engine bolted on, that it exists twice, that there is a caching proxy between it and the world, and that authors edit content in the same system that serves it. Everything in Part II follows from those.

The repository is a filesystem, and your code lives in it

AEM stores everything in a JCR repository: content, configuration, templates, and your code. Paths matter and are conventional.

PathWhat lives there
/content/<site>/<locale>/…Pages. Each page is a node with a jcr:content child holding the components.
/content/dam/Assets. Images, PDFs, and Content Fragments.
/apps/<project>/components/Your components: HTL templates plus dialog definitions.
/apps/<project>/clientlibs/Client libraries. This is where a bundle goes in pattern 1.
/etc.clientlibs/<project>/…The public proxy path for client libraries. Requires allowProxy.
/conf/<project>/Templates, policies, and Sling context-aware configuration.
/libs/Adobe's own code. Never write here.
/apps is deny-by-default at the dispatcher. That is why client libraries are served from /etc.clientlibs instead. The proxy servlet maps the public path back to the real one, and it only works if the client library node sets allowProxy="{Boolean}true". Chapter 10 shows the file.

HTL, in the amount you need

HTL is AEM's template language. It is server-side, it auto-escapes by context, and for front-end purposes you need about five constructs.

Do not turn off escaping

@ context='unsafe' disables HTL's cross-site-scripting protection. There is almost never a good reason on a page that renders author-supplied content. If you need raw HTML from a rich text field, use context='html', which allows markup but still strips scripts.

Sling Models produce the JSON your bundle reads

A Sling Model is a Java class that adapts a repository node into a typed object, and can be serialised to JSON by requesting a .model.json selector. This is the seam between the AEM half of the project and yours.

Pattern 1: client libraries

The oldest way in, and still the right one for global behaviour. Categories, dependencies, the proxy flag, and how to generate all of it from an Nx build.

A client library is a node in the repository that holds CSS and JavaScript, declares a category name, and can declare dependencies on other categories. HTL includes them by category. AEM concatenates, minifies and versions them. That is the entire model.

The node structure

Three attributes, three distinct failure modes

  • categories missing or misspelled: the library exists and is never served. No error anywhere.
  • allowProxy missing: works on author, 404s at the dispatcher on publish. This is the classic "it worked in my local instance" bug.
  • dependencies wrong: files load in the wrong order and you get a runtime error that looks like a bundling problem.

Including it from HTL

clientlib.all exists and you should not use it. It emits CSS and JS together in one place, which puts your JavaScript in the head or your stylesheet at the end of the body. Call css and js separately so you control where each lands.

Generating the clientlib from an Nx build

You do not hand-write js.txt. aem-clientlib-generator takes a build output directory and writes the whole node structure. As of 10 September 2026 it is at version 2.0.3.

Note the inputs entry for the config file

This is the chapter 2 trap in its most common real form. The generator reads clientlib.config.js, so a change to it must change the hash. Without that line, editing the category name produces a cache hit and deploys the old node structure.

Cache busting

AEM appends a hash to client library URLs when longCacheKey is set, producing paths like clientlib-site.lc-<hash>-lc.min.js. Combined with a long Cache-Control at the dispatcher, this gives correct immutable caching. Without it you are relying on the dispatcher's TTL and will serve stale JavaScript after a deploy. Chapter 15 covers the dispatcher side.

Pattern 2: islands as custom elements

AEM renders the page. Angular renders three components inside it. The seam is a custom element and a handful of data attributes, and it is the most useful pattern in this book.

This is the pattern to reach for by default. AEM keeps the page, the URL, the Page Editor and the author workflow exactly as they are. Angular gets the components that genuinely need a component framework. Nothing has to be rewritten to add the second island.

The contract

An island has a narrow, deliberate interface, and writing it down before you write code is what stops it becoming a mess.

  1. AEM emits a custom element with a hyphenated tag name.
  2. Configuration arrives as data-* attributes rendered by HTL from the Sling Model.
  3. The island fetches its own data, or receives an initial payload in a <script type="application/json"> child.
  4. The island communicates outward by dispatching CustomEvents that bubble and compose.
  5. It renders nothing until upgraded, and the server provides a skeleton so the layout does not shift.

Defining the element

createApplication plus createCustomElement is the supported route. It gives you a real Angular injector, so dependency injection, HttpClient and providers all work, without bootstrapping a routed application.

One application, many elements. createApplication is called once and its injector is shared by every element. Calling it per element gives each island its own copy of every root-provided service, which is almost never what you want and is a real memory cost on a page with eight islands.

The component side

Signal inputs map onto attributes automatically. Angular converts a hyphenated attribute to the camel-case input name, so data-currency does not map: use a plain currency attribute, or read data-* explicitly from the host element.

The HTL side

Author mode is the thing everyone forgets

In the Page Editor, AEM overlays every component with a clickable region. An island that binds pointer handlers, or that repaints its own subtree, fights that overlay. Authors report "I cannot select the component". Detect wcmmode.edit in HTL and render a static placeholder. Do not try to solve it in JavaScript.

Bundling as an IIFE

The Angular application builder emits ES modules with hashed filenames and an import graph. Client libraries concatenate files in js.txt order into one classic script. Those two models do not meet. The fix is a second, tiny esbuild pass that produces one self-contained IIFE.

Why not just use the Angular builder output? You can, if you are on pattern 3, or if you inject a <script type="module"> tag yourself rather than going through a client library. The moment AEM's clientlib concatenation is in the path, ES module output stops working, because concatenating modules is not a thing.

Size, honestly

An Angular island is not free. A realistic zoneless bundle with two components, HttpClient and no router lands around 45 to 70 kB compressed. That is fine for a cart. It is not fine for a "read more" toggle.

Pattern 3: headless and the Universal Editor

Your application owns the document. AEM owns the content. The Universal Editor is the bridge, and its contract is three meta tags, one script and nine attributes.

The Universal Editor is Adobe's replacement for the SPA Editor and the visual editor its roadmap now prioritises. Its central design decision is worth understanding before you write any code: it needs no AEM-specific SDK in your application. You instrument the DOM you already render, and an editor loaded in a parent frame reads that instrumentation.

One thing that has moved since most tutorials were written

The npm package @adobe/universal-editor-cors is deprecated. Its own README states the library should no longer be used and that support stopped on 31 May 2025. Do not npm install it. The integration is the hosted script tag shown below.

The instrumentation contract

Three pieces. The values below were read out of Adobe's shipped Universal Editor bundle, not recalled from documentation.

1. The connection meta tags

Meta tags in the document head declare where edits are persisted. The name follows urn:adobe:aue:<category>:<referenceName> where category is system or config, and the content is <protocol>:<url>. The editor finds them with the selector meta[name^='urn:adobe:aue:'].

2. The data-aue-* attributes

The default attribute prefix is data-aue-. The full suffix set, straight from the bundle's frozen constant map:

AttributePurpose
data-aue-resourceThe content this element renders, as a URN: urn:aemconnection:/content/acme/en/home/jcr:content/hero.
data-aue-typeWhat kind of editable this is: text, richtext, media, reference, container, component.
data-aue-propThe property on the resource this element maps to.
data-aue-labelThe human-readable name shown in the editor rail.
data-aue-modelThe model id defining the fields available in the properties panel.
data-aue-filterRestricts which components may be added inside a container.
data-aue-behaviorEditing behaviour override, typically component to make a whole subtree act as one unit.
data-aue-idExplicit identity, used when a resource URN is not sufficient to disambiguate.
data-aue-parentidExplicit parent, when the DOM hierarchy does not reflect the content hierarchy.

3. The events

The editor dispatches DOM events your application can listen for. Handle them if you want in-place updates without a reload.

Instrumenting Angular templates

Writing the attributes by hand in every template is noisy and easy to get wrong. A directive keeps the contract in one place.

Instrument in both modes. The attributes are inert outside the editor. Stripping them for production is a micro-optimisation that costs you the ability to point the editor at a real environment, and reintroduces the "works in dev only" class of bug.

Reading content

Two routes, and they answer different questions. GraphQL persisted queries for Content Fragments. The Sling Model exporter for page-structured content.

Persisted queries are not an optimisation

They are the only viable delivery mechanism. A persisted query is a GET against a cacheable path, so the dispatcher and CDN can cache it. An ad-hoc POST to /content/_cq_graphql/…/endpoint.json is uncacheable by design and is blocked by the default dispatcher filters on publish. Building against POST on a local author instance and discovering this at the first publish deploy is a rite of passage worth skipping.

CORS, which is where most Universal Editor setups actually fail

The editor loads your application in a frame from a different origin and needs to talk to AEM. Both sides need configuration, and the symptom of getting it wrong is an editor that loads your page but shows no editable regions.

When pattern 3 is actually right

It is the right answer when your application genuinely owns the experience: a configurator, a booking flow, an authenticated portal, a product catalogue with heavy client-side filtering. It is the wrong answer when you have 400 authored marketing pages and one interactive component, because you would be rebuilding the 400 to accommodate the one.

Pattern 4: the SPA Editor you inherited

Deprecated, still supported, still running in production somewhere near you. How it works, how to keep it alive, and what a realistic exit looks like.

Read this before the rest of the chapter

The AEM SPA Editor is deprecated. Adobe's AEM 6.5 deprecation page cites release 6.5.23; the AEM 6.5 release notes say 6.5.25. Both pages are current and they disagree, so quote the range rather than a number. On AEM as a Cloud Service the deprecation landed with release 2025.01. What deprecation means here, in Adobe's own terms: no further enhancements or updates to the SDKs, P1 and P2 issues and security vulnerabilities only, existing implementations remain supported and may continue, and there is no direct migration path to the Universal Editor. Do not start a new project on this pattern. This chapter is for the one you already own.

The SPA Editor's idea was that AEM would export the page as a JSON model, a React or Angular application would render it, and a mapping layer would connect each JSON node back to an editable component so authors could still drag and drop. It worked, and the coupling it required is exactly why it is being replaced.

The SDKs, all now frozen

Adobe lists the following as in feature freeze. If your project depends on any of them, you are on this pattern.

PackageRole
@adobe/aem-spa-page-model-managerFetches and caches the page model JSON, handles routing updates.
@adobe/aem-spa-component-mappingThe registry mapping a resource type to a component class.
@adobe/aem-angular-editable-componentsAngular bindings: the container components and the editable decorator.
@adobe/aem-react-editable-componentsThe React equivalent, plus the React core component families.
AEM Project ArchetypeThe generator for the whole SPA-editor project shape.

How it actually works

Why the decorators. These SDKs predate signal inputs and expect the decorator API. Mixing signal inputs into a MapTo-registered component is where most "modernise it in place" attempts stall, because the container sets properties imperatively in a way signal inputs do not accept.

Keeping it alive

A frozen SDK does not mean a frozen application. Three rules make maintenance sustainable.

  1. Quarantine the SDK. Put every import from an @adobe/aem-spa-* package behind one library, tagged type:data-access, and ban the imports everywhere else with bannedExternalImports. Feature code should not know these packages exist.
  2. Pin exactly. No carets. These packages will not receive fixes, so a range buys risk and no benefit.
  3. Test the model shape, not the SDK. Your contract is the JSON. Snapshot a real .model.json response and assert your adapters against the fixture. Then an AEM upgrade that changes the export shows up as a failing test rather than a blank page.

What an exit actually looks like

Adobe is explicit that there is no automated conversion, and about why: the Universal Editor is an editor-as-a-service and cannot accept injected dialog CSS or JavaScript, so component dialogs cannot be translated. It also deliberately does not reintroduce the Template Editor, the Style System or the Responsive Grid. If your site leans on those, an exit is a redesign, not a port.

Adobe's own recommendation is the pragmatic one: keep existing SPA Editor sites as they are, since support continues, and adopt the Universal Editor for new sites, sections and pages. In practice that means:

  • Freeze the SPA Editor surface. No new component types on it.
  • Build new sections on pattern 3, with their own routes, sharing your Nx libraries. The presentational libraries port cleanly, because they never imported the SDK if you followed rule 1.
  • Move page groups across when they are being redesigned anyway. Never as a standalone migration project, because there is no user-visible benefit to fund it with.
  • Accept that two editors will coexist for a long time, and make that explicit in author training rather than a surprise.

Where the workspace lives

One repository or two, and how the Nx build meets the Maven build without either owning the other.

AEM projects are Maven projects. Nx workspaces are npm projects. Somewhere the two have to meet, and the shape of that meeting determines whether a front-end change takes ten minutes or a full AEM deploy.

Three shapes

A. One repository, Nx at the root, AEM as a subdirectory

This is the shape to prefer. One commit changes a component's HTL and its Angular island together, and CI can prove both. Nx owns the JavaScript graph, Maven owns packaging, and neither is nested inside the other's source tree.

B. Two repositories

Front-end publishes versioned packages, AEM consumes them. Choose this only when a hard organisational boundary exists: a separate agency owns the AEM side, or compliance requires separate access. It reintroduces exactly the release-ordering problem chapter 1 opened with, so make it a deliberate trade rather than a default.

C. AEM archetype at the root, Nx inside ui.frontend

Common because the archetype generates it, and it fights you. Nx wants to be at the repository root: defaultBase, affected calculations and the .nx cache all assume it. Buried under ui.frontend, the affected calculation cannot see changes to HTL or Java that should invalidate a front-end build. It works for one application and degrades from there.

Making Maven call Nx

The bridge is frontend-maven-plugin, which downloads a pinned Node and npm and runs a script. The archetype wires it into generate-resources so the front-end build happens before packaging.

Use run-many here, not affected

A Maven build has no notion of a git range and often runs on a detached checkout with no base ref. nx affected in that context quietly resolves to everything, or to nothing, and which one you get depends on the checkout. Keep affected in the CI workflow, where the SHAs are set explicitly, and let Maven ask for a deterministic run-many. The Nx cache still makes it fast.

The generated output is not source

The clientlib directory that aem-clientlib-generator writes into ui.apps is build output. Commit it and you get merge conflicts in minified JavaScript, which nobody can resolve.

Ignore the generated folders, not the whole clientlibs directory. Hand-written client libraries, particularly the author-only one from chapter 10, live alongside the generated ones and must stay tracked. List the generated names explicitly.

The local development loop

aemsync watches the jcr_root tree and pushes changed nodes into a running author instance over the package manager API. Combined with nx watch, saving a component file rebuilds the affected island, regenerates the clientlib, and pushes it, in a few seconds. Without it you are running a Maven install per change, which is a minute or more and destroys the feedback loop.

Caching, the dispatcher and performance

The dispatcher is a deny-by-default proxy with a disk cache. Understand its filter syntax and its invalidation model, or spend your career debugging stale pages.

Every performance problem on an AEM site is one of three things: the dispatcher is not caching what it should, it is caching what it should not, or your bundle is too big. The third one is your problem alone. The first two are configuration, and the configuration is small enough to read in full.

Filters: deny everything, then allow

Filters are an ordered ACL. The shipped default set opens with a total deny and then allows specific things back. Rules are evaluated in order and the last match wins, which is why custom rules use high numbers.

Test the filters, do not read them. curl -I against a publish-tier dispatcher is the only reliable check. Reading the merged rule set by eye across an include and twenty numbered entries is how allow rules get shadowed by later denies.

The cache, and the two headers that matter

The dispatcher caches responses to disk, keyed by request path. Two separate mechanisms decide freshness, and confusing them is the usual cause of "I invalidated and it is still stale".

MechanismControlsInvalidated by
Dispatcher disk cacheWhat the dispatcher serves without asking AEM.A replication flush from AEM, or statfile touch, or a manual delete.
Cache-Control headerWhat the CDN and the browser keep.Nothing. It expires on time, or on a changed URL.

A content author publishing a page flushes the dispatcher. It does not reach the CDN or anyone's browser. That is why immutable, content-hashed URLs matter so much: they are the only reliable invalidation for anything downstream of the dispatcher.

The single most expensive mistake in this chapter

Marking an unhashed URL immutable. Once a browser has cached site.js for a year with no hash in the path, you cannot recall it. Not by deploying, not by flushing the dispatcher, not by purging the CDN. The only fix is to change the URL, which means every page that references it must also be reissued. Only ever pair immutable with a content hash in the path.

Multi-brand, multi-locale, multi-team

One workspace, six brands, twenty locales, four teams. The library layout that holds and the two that do not.

Multi-brand is where library design stops being an aesthetic preference and starts being the thing that determines whether a release is possible. The failure is always the same: a change for brand A cannot ship because brand B has not finished testing, because they share a library that encodes both their behaviours.

Separate the three axes

Brand, locale and team are three different problems and want three different mechanisms. Conflating them is the root of most of the pain.

AxisVariesMechanismNot this
BrandColour, type, spacing, logo, occasionally a component variant.CSS custom properties, one token file per brand.A library per brand.
LocaleStrings, dates, currency, text direction.Runtime message files loaded by locale.A build per locale.
TeamOwnership and release cadence.Scope tags, CODEOWNERS, separate apps.Separate repositories.

Brand as tokens, not as code

Ship one component library. Ship one bundle. Change the values, not the code. The moment a component reads a brand identifier and branches, you have coupled the brands together and every future change needs testing against all of them.

The rule that keeps this honest

No component in shared-ui may read the brand. Not through a service, not through an input, not through a CSS attribute selector inside the component. If a brand needs a different structure rather than different values, that is a variant component with an explicit name, chosen by the author in a dialog. Once one component branches on brand, the pattern is dead and every subsequent one will too.

Locale as data, not as builds

Angular's compile-time i18n produces one bundle per locale. With twenty locales that is twenty builds, twenty cache entries, twenty artifacts to promote, and a dispatcher configuration that has to route to the right one. For AEM work, load messages at runtime instead.

Right-to-left is not a locale file. It is CSS logical properties. Use margin-inline-start rather than margin-left throughout shared-ui from day one. Retrofitting logical properties across a component library is a genuinely large piece of work and adding Arabic is when you find out.

Team as scope and ownership

Pair that with the scope constraints from chapter 5 and the boundary is enforced twice: the lint rule stops the import, and CODEOWNERS stops the merge. Neither alone is sufficient, because a determined engineer can add a tag, and a reviewer cannot see an import they were not asked to look at.

Two layouts that do not work

A library per brand. libs/northwind/ui, libs/seabright/ui, and so on. It looks like clean separation and it is duplication. A fix to the date picker has to be applied six times, and within a year the six have drifted enough that they cannot be reunified.

A build per brand and locale. Six brands times twenty locales is a hundred and twenty artifacts. The cache is useless because nothing is shared, CI runs for hours, and the artifact you tested is not the artifact you shipped for a hundred and nineteen of them.

Field guide to things that break

Symptom, cause, fix. Ordered by how often you will meet them, not by how interesting they are.

Everything here has cost somebody a day. They are grouped by where the symptom appears, because that is how you will encounter them: something is wrong on the page, and you have to work backwards.

It works on author, not on publish

Client library 404s

Cause: allowProxy is missing from the client library node. Author often serves /apps directly; publish sits behind a dispatcher that denies it.
Fix: allowProxy: true in clientlib.config.js, then verify the generated .content.xml actually contains it. See chapter 10.

GraphQL returns nothing

Cause: ad-hoc POST queries. The dispatcher denies them and they would be uncacheable anyway.
Fix: persisted queries, which are GETs on allowed paths. See chapter 12.

A JSON endpoint 404s only on publish

Cause: no filter rule for that selector or extension. The default filter set denies everything not explicitly allowed.
Fix: add a numbered allow rule in filters.any, then confirm with curl -I against publish rather than by reading the file.

It works locally, not in CI

nx affected selects everything

Cause: shallow clone. No merge base, so Nx falls back to all projects.
Fix: fetch-depth: 0 on actions/checkout, plus nrwl/nx-set-shas@v5 with actions: read. See chapter 7.

A cached build ships stale content

Cause: the task reads a file that is not in its inputs. Brand tokens, clientlib config and generated files are the usual suspects.
Fix: add the path to the target's inputs. Reproduce it once deliberately so you recognise the shape. See chapter 2.

The cache never hits

Cause: the opposite. An input glob covers something that changes every run: a timestamp file, a lockfile rewritten by the install step, or an output directory that is also an input.
Fix: run with --verbose and read the input list. The offender is usually obvious once printed.

It works, then stops after a deploy

Browsers keep old JavaScript forever

Cause: Cache-Control: immutable on a URL with no content hash.
Fix: there is no fix for the copies already out there. Change the URL. Then pair immutable only with hashed paths. See chapter 15.

A page is stale after publishing

Cause: the dispatcher flushed but the CDN did not. A replication flush reaches the dispatcher only.
Fix: shorter s-maxage on HTML, or an explicit CDN purge in the publish workflow.

It breaks only sometimes

The bundle dies on some pages with NotSupportedError

Cause: customElements.define called twice, because a client library was included twice through nested templates.
Fix: guard with customElements.get(tag). See chapter 11.

An island renders twice

Cause: the element is both server-rendered as a skeleton and re-inserted by JavaScript, or two clientlib categories both define it.
Fix: the skeleton belongs inside the custom element as light DOM, so upgrading replaces it. Never as a sibling.

Something updates in one browser and not another

Cause: zoneless change detection plus a plain field mutation. Whether it repaints depends on whether something else nearby triggered detection.
Fix: the state belongs in a signal. See chapter 6.

Authors report it, engineers cannot reproduce it

"I cannot select the component"

Cause: an island is intercepting pointer events meant for the Page Editor overlay.
Fix: render a static placeholder under wcmmode.edit. See chapter 11.

"The Universal Editor shows the page but nothing is editable"

Cause: almost always CORS, occasionally a missing aemconnection meta tag, occasionally the connection pointing at publish.
Fix: open the browser console first. A CORS rejection is explicit and named. See chapter 12.

"It looks wrong in the editor but right on the site"

Cause: the editor renders your page in an iframe at a different width, and container queries or viewport units resolve differently.
Fix: use container queries deliberately, and test at the editor's frame width, not just at device breakpoints.

Build and tooling

Two copies of RxJS in the bundle

Cause: a version range in a library's own package.json that does not match the root.
Fix: one version at the root, no per-library dependency versions. banTransitiveDependencies catches the related class of problem.

The IIFE bundle is much larger than expected

Cause: a type:util library imported @angular/core for one pipe, pulling the framework into a bundle that did not need it.
Fix: the bannedExternalImports rule from chapter 5 exists precisely for this and turns it into a lint error.

A Maven build produces an empty clientlib

Cause: nx affected in the Maven step resolved to nothing, because there is no git range in that context.
Fix: run-many in Maven, affected in CI. See chapters 14 and 16.

Why AWS sits beside AEM

Not a migration, not a replacement. A small set of things AEM is a bad fit for, and one CloudFront distribution that hides the seam.

Nearly every AEM estate grows an AWS account. Not because anyone decided to go multi-cloud, but because a requirement turned up that AEM is genuinely the wrong tool for, and someone shipped a Lambda. This part is about doing that deliberately.

One origin, or two

Cache policy per behaviour, not per distribution

The three behaviours need genuinely different caching. /api/* forwards Authorization and caches nothing. It is not a strangler pattern. There is no plan here to gradually move AEM's responsibilities to AWS. The dispatcher stays the default origin, AEM keeps the content, and the AWS side handles the specific set of requirements from the table above. Framing it that way keeps the surface small and stops the AWS account becoming a second, undocumented CMS.

Data, storage and the services you actually need

A shared contract library, one DynamoDB table, presigned S3 uploads, and a Lambda handler with no framework in it.

The AWS surface for an AEM companion API is small: one table, one bucket, a handful of functions. The interesting engineering is not in the services, it is in keeping the browser and the function honest about the shape of the data between them.

The contract library

Put the schemas in a library both sides import. Zod gives runtime validation and static types from one declaration, so the type cannot drift from the check. As of 10 September 2026 Zod is at 4.6.1.

Tag it type:util and mean it. The contract library is imported by browser code and by Lambda code, so it must contain nothing platform-specific. The bannedExternalImports rule from chapter 5 already stops @angular/* reaching it. Add aws-sdk and @aws-sdk/* to the same list.

One table, not five

DynamoDB single-table design means one table holding several entity types, distinguished by key prefixes. It exists because DynamoDB has no joins: if you need a customer and their carts in one request, they must share a partition.

Presigned uploads

The browser gets a short-lived URL and PUTs directly to S3. The bytes never touch your Lambda, so there is no payload limit and no execution time spent moving data.

Three rules for presigned PUTs

  1. The server picks the key. A client-supplied key is a path traversal and an overwrite of someone else's object.
  2. Pin ContentType and ContentLength in the signature. Without them the URL accepts anything of any size.
  3. Expire in minutes, not hours. A leaked URL is a write grant for its whole lifetime.

The handler

No framework. An API Gateway HTTP API event is a plain object, and a router for six routes is thirty lines you can read.

Building and shipping it from one workspace

A CDK stack as an Nx project, Lambda bundling that respects the graph, and one pipeline that deploys both halves without either knowing about the other.

The point of Part III is not the AWS services. It is that the API, the infrastructure and the AEM front end are three projects in one workspace, sharing one contract library, validated by one affected build. A change to a Zod schema fails the pipeline on both sides in the same pull request. That is the whole argument, and it is the same argument as chapter 1.

The infrastructure as a project

Do not let CDK bundle your Lambda. NodejsFunction runs esbuild inside cdk synth, which puts a build step inside the deploy step where Nx cannot see or cache it. Build with an Nx target, then hand CDK a directory. The graph stays honest and the bundle is cached.

Bundling the function

Which targets are cacheable

build and synth are pure functions of their inputs, so they cache. deploy and diff read remote state that Nx cannot hash, so cache: false is correct and not a compromise. Caching a deploy would mean skipping it because nothing local changed, which is exactly wrong when the remote has drifted.

One pipeline, both halves

What this buys you

Change CartLine in libs/api-contract and run nx affected -t build. The affected set contains the contract library, the data library, the API application, the infrastructure project, the cart feature library, and both front-end applications. One command proves the browser and the function still agree, before merge.

That is the same property from chapter 2, applied across a boundary that would otherwise be a versioned npm package and a coordinated release. It is worth restating plainly: the reason to put the AWS side in the workspace is not tidiness. It is that the contract between the browser and the function is the thing most likely to break, and this is the only arrangement where a single command checks it.

Back matter · Appendix B

B

Glossary

The terms that mean something specific in this book, and a few that mean something different in AEM than elsewhere.

Nx and the workspace

Affected
The set containing the projects whose files changed between two git revisions, plus every project that transitively depends on them. Computed by walking the project graph upward. Chapter 2 has a widget for it.
Executor
The implementation behind a target. nx:run-commands runs a shell command; @angular/build:application runs the Angular builder.
Inferred target
A target Nx creates from the presence of a config file, without any entry in project.json. nx show project prints the merged result.
Named input
A reusable file set used in hashing. production conventionally excludes tests, so a spec edit does not invalidate a downstream build.
Project graph
The directed graph Nx derives from your imports. Not maintained by hand, so it cannot drift from the code.
Target
A named operation a project can perform: build, test, lint, build-aem.
Task hash
The cache key for one task, derived from its resolved inputs, its dependencies' output hashes, the command and the relevant configuration.
^ prefix
In dependsOn, means "of my dependencies". ^build is "the build target of everything I depend on".

Angular

Custom element
A browser-native component with a hyphenated tag name. Angular produces one with createCustomElement. The seam for pattern 2.
Island
A framework component mounted inside a page rendered by something else. Not an Angular term; the pattern name from chapter 11.
Signal
A reactive value read as a function. The unit of change detection in a zoneless application.
Signal input
input() and input.required(). Replaces the @Input() decorator and composes into computed() without a lifecycle hook.
Zoneless
Change detection driven by signal writes and template events rather than by Zone.js patching global browser APIs. Provided by provideZonelessChangeDetection(), stable since Angular 20.2.

AEM

Author / Publish
The two AEM tiers. Authors edit on author; visitors read from publish. Content is replicated between them; code is deployed to both.
Client library (clientlib)
A repository node holding CSS and JavaScript, identified by a category name, included from HTL by category.
Content Fragment
Structured, presentation-free content, queried over GraphQL. The usual source for headless delivery.
Dispatcher
The Apache module in front of publish. A deny-by-default filter chain plus a disk cache. Chapter 15.
HTL
HTML Template Language. AEM's server-side template language, context-escaping by default.
JCR
Java Content Repository. The tree that stores content, configuration and code.
Page Editor
The classic in-context editor for AEM-rendered pages. Patterns 1 and 2 keep it.
Persisted query
A named GraphQL query stored in AEM and executed by a GET on a cacheable path. The only viable GraphQL delivery mechanism on publish.
Sling Model
A Java class adapting a repository resource into a typed object, optionally exported as JSON.
SPA Editor
The deprecated editor for application-rendered pages, built on the page model JSON and a component mapping registry. Chapter 13.
Universal Editor
Adobe's current visual editor. Needs no AEM-specific SDK: it reads data-aue-* attributes and urn:adobe:aue:* meta tags from whatever HTML your application renders. Chapter 12.
wcmmode
The rendering mode: edit, preview or disabled. Readable in HTL, and the correct place to decide whether an island should mount.

Delivery and AWS

Front-end pipeline
A Cloud Manager pipeline that builds only a nominated folder containing a package.json and deploys the output to the built-in CDN, served from a static-p<program>-e<env> hostname.
Full-stack pipeline
A Cloud Manager pipeline that builds the whole Maven reactor and deploys to author, publish and the dispatcher.
Immutable
A Cache-Control directive promising the bytes at this URL will never change. Safe only with a content hash in the path.
Presigned URL
A time-limited, signed S3 URL granting one operation on one key. The key is part of the signature, so it must be chosen by the server.
Single-table design
Holding several DynamoDB entity types in one table, distinguished by key prefixes, so related items share a partition and can be read in one query.
